# Диагностика

Порядок важен: сначала убеждаемся, что виноват не конфиг, и только потом лезем
в сеть.

---

## `warp-vps verify` говорит `warp=off`

Интерфейс поднят, трафик до интернета доходит, но Cloudflare не считает его
WARP-трафиком.

**Не направляйте на него Xray.** Пользователи получат выход с реального IP
ноды, молча.

Что проверить:

```bash
warp-vps status
```

- `Handshake: none` — соединения с Cloudflare нет вовсе, см. следующий раздел.
- Handshake свежий, а `warp=off` — почти всегда endpoint, который отвечает, но
  выводит не в WARP. Лечится переездом: `warp-vps rotate`.

---

## Нет handshake

```bash
warp-vps rotate
```

Если после двух-трёх смен endpoint'а handshake так и не появился — блокируется
не адрес, а сам WireGuard-трафик до Cloudflare. Проверьте, уходит ли UDP:

```bash
ss -unp | grep -i wireguard
journalctl -u wg-quick@warp -n 40 --no-pager
```

Провайдеры, режущие UDP на нестандартных портах, — частая причина. Пул портов
у нас `2408 / 500 / 1701 / 4500`; 500 и 4500 это IPsec, их обычно не трогают,
так что несколько `rotate` подряд имеют смысл.

## `install` возвращает 403

```
Cloudflare refused the request (HTTP 403)
```

Два разных случая.

**Блокировка IP датацентра.** Cloudflare не любит регистрации из хостинговых
подсетей. Зарегистрируйте с другой машины и перенесите файл:

```bash
scp /etc/warp-vps/account.json root@node:/etc/warp-vps/account.json
```

Ключ к адресу не привязан — аккаунт работает откуда угодно. Затем на ноде
`warp-vps install` (он подхватит существующий аккаунт) .

**Несовпадение TLS-профиля.** Если 403 приходит и с домашнего IP, проверьте,
умеет ли ваш curl ограничивать верхнюю границу TLS:

```bash
curl --tlsv1.2 --tls-max 1.2 --http1.1 -sSI https://api.cloudflareclient.com | head -1
```

Сборки с некоторыми TLS-бэкендами `--tls-max` игнорируют, предлагают TLS 1.3 и
получают 1020.

## `install` возвращает 429

Лимит по IP. Подождите несколько минут.

## Интерфейс поднят, но Xray им не пользуется

Симптом: `warp-vps verify` зелёный, а клиенты выходят с адреса ноды.

**Xray не видит интерфейс.** Контейнер ноды должен делить сетевое пространство
имён с хостом:

```bash
docker inspect remnanode --format '{{.HostConfig.NetworkMode}}'   # ожидается: host
docker exec remnanode ip link show warp                            # интерфейс должен быть виден
```

**Нет прав на привязку.** `SO_BINDTODEVICE` требует `CAP_NET_ADMIN`. В логах
ноды при старте должно быть `[HandlerService] [OK] CAP_NET_ADMIN is available`.

**Правило не сработало.** Xray берёт **первое совпавшее** правило, а не самое
специфичное: правило с `outboundTag: "warp"` обязано стоять выше любого
catch-all. И если в конфиге catch-all нет вообще, несовпавший трафик уходит в
**первый** outbound массива — поэтому `warp` никогда не должен быть первым.

**Правило по домену, а клиент ходит по IP.** Тогда `domain`-условие не
срабатывает. Включите `sniffing` на inbound, чтобы Xray восстанавливал имя из
TLS SNI.

## Как понять, принимает ли сервис новый IP

`warp=on` доказывает только, что пакеты идут через Cloudflare. Примет ли адрес
сам сервис — вопрос отдельный:

```bash
warp-vps verify --probe ai
```

**Не проверяйте это, дёргая HTML-корень сайта.** `curl https://chatgpt.com`
вернёт `403` откуда угодно, включая домашний браузерный IP: Cloudflare отбивает
curl по TLS-отпечатку, а не по адресу — браузерный User-Agent ничего не меняет,
проверено. Такой `403` про вашу репутацию не говорит ничего.

Пресет `ai` спрашивает эндпоинты, которые отвечают честно:

| Эндпоинт | Что означает ответ |
|---|---|
| `.../cdn-cgi/trace` | бот-защитой не прикрыт; `200` плюс строка `ip= loc= warp=` — то, каким сервис видит соединение |
| `api.openai.com/v1/models` | `401` = дошли, нет ключа. `403` = блокировка |
| `gemini.google.com` | `200` = доступен |

Окончательный ответ даёт браузер через готовый VPN: логин-флоу и антифрод
смотрят на куда больше признаков, чем адрес.

## Медленно / рвётся на тяжёлых страницах

Классический MTU-симптом: короткие запросы летают, крупные виснут.

Не подбирайте вслепую — измерьте. MTU туннеля выводится из MTU пути до
endpoint'а:

```
MTU туннеля = PMTU до endpoint − 60
```

60 байт — накладные расходы WireGuard поверх IPv4: 20 (IP) + 8 (UDP) +
16 (заголовок data-пакета) + 16 (тег Poly1305).

```bash
EP=$(warp-vps status 2>&1 | awk '/Endpoint/{print $2}' | cut -d: -f1); for s in 1472 1452 1422 1372 1332 1272 1232; do ping -M do -s $s -c1 -W2 "$EP" >/dev/null 2>&1 && { echo "PMTU=$((s+28)) -> MTU $((s+28-60))"; break; }; done
```

Полученное значение правится в `/etc/wireguard/warp.conf` (`MTU = …`), затем
`systemctl restart wg-quick@warp`.

Два случая, когда способ не работает:

- **ICMP отфильтрован** — цикл ничего не выведет. Тогда 1280 остаётся
  осознанным консервативным выбором.
- **PMTU до Cloudflare нормальный, а виснет конкретный сайт.** Тогда дело в
  PMTU дальше по пути, и `MTU` туннеля не поможет.

Если медленно **равномерно** — смотрите не MTU, а CPU: `top -bn1 | head -5`,
интересует `%si` (softirq), там живёт шифрование.

## Что собрать перед тем, как просить помощи

```bash
warp-vps status
warp-vps verify --probe ai 2>&1 | tail -30
journalctl -u warp-vps-watchdog.service -n 30 --no-pager
jq 'del(.private_key, .access_token)' /etc/warp-vps/account.json
```

Последняя команда безопасна для пересылки: приватный ключ и токен из неё
вырезаны. Файл целиком не отправляйте никогда.
