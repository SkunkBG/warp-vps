# Диагностика

Порядок важен: сначала убеждаемся, что виноват не конфиг, и только потом лезем в
сеть.

---

## `warp-vps verify` говорит `warp=off`

Туннель поднялся, трафик до интернета доходит, но Cloudflare не считает его
WARP-трафиком. Значит, outbound выпускает пакеты каким-то другим путём.

**Не раскатывайте это в продакшен** — пользователи получат выход с реального IP
ноды, молча.

Проверьте по порядку:

1. `peer_public_key` в файле аккаунта — это ключ Cloudflare, не ваш. Он должен
   отличаться от вашего `public_key`.
2. `reserved` — ровно 3 байта, полученные из `client_id`. Попробуйте
   `warp-vps refresh`: `client_id` мог смениться.
3. `endpoint` — если вы задавали `--endpoint random`, адрес мог оказаться
   нерабочим. Вернитесь на `--endpoint api`.

## Xray не поднимает SOCKS-порт в `verify`

`verify` в этом случае печатает лог Xray. Смотрите первую строку ошибки.

### `failed to disable ipv4 rp_filter for all: read-only file system`

Включён ядерный TUN в контейнере без прав. Уберите `--kernel-tun` — это ровно
тот случай, ради которого `noKernelTun: true` стоит по умолчанию.

### `"reserved" should be empty or 3 bytes`

Файл аккаунта повреждён или отредактирован руками. `warp-vps refresh` перечитает
`client_id` из Cloudflare.

### `unsupported domain strategy`

Значение `--domain-strategy` не из списка. Допустимы: `ForceIP`, `ForceIPv4`,
`ForceIPv6`, `ForceIPv4v6`, `ForceIPv6v4`.

### `invalid WireGuard secret key`

Ключ не в base64 и не в hex, либо обрезан. Перерегистрируйте аккаунт.

## `register` возвращает 403

```
Cloudflare refused the request (HTTP 403)
```

Два разных случая, лечатся по-разному.

**Блокировка IP датацентра.** Cloudflare не любит регистрации с хостинговых
подсетей. Зарегистрируйте аккаунт с другой машины (хоть с ноутбука) и перенесите
`*.account.json` на ноду — ключ к IP не привязан, аккаунт будет работать откуда
угодно.

**Несовпадение TLS-профиля.** Если 403 приходит и с домашнего IP, проверьте, что
ваш curl вообще умеет ограничивать верхнюю границу TLS:

```bash
curl --tlsv1.2 --tls-max 1.2 --http1.1 -sSI https://api.cloudflareclient.com | head -1
```

Сборки curl с некоторыми TLS-бэкендами `--tls-max` игнорируют, предлагают TLS 1.3
и получают 1020. Лечится другим curl.

---

## `register` возвращает 429

Cloudflare лимитирует регистрации по IP. Подождите несколько минут.

При массовой регистрации увеличьте паузу:

```bash
./warp-vps.sh batch --count 10 --delay 30
```

## Правило маршрутизации есть, но трафик идёт мимо WARP

Почти всегда — **порядок правил**. Xray берёт первое совпавшее, не самое
специфичное. Правило с `outboundTag: "warp"` должно стоять выше любого
catch-all, отправляющего трафик в `direct`.

Второй по частоте случай — правило написано по домену, а клиент ходит по IP.
Тогда `domain`-правило не срабатывает вообще. Добавьте `ip`-условие или включите
`sniffing` на inbound, чтобы Xray восстанавливал имя из TLS SNI.

## Работает, но медленно / рвётся на тяжёлых страницах

Классический MTU-симптом: короткие запросы летают, крупные виснут.

Сначала убедитесь, что в outbound действительно `"mtu": 1280`, а не 1420 — Xray
подставляет 1420, когда поле опущено.

Если 1280 не помогло, **не подбирайте вслепую** — измерьте. MTU туннеля
однозначно выводится из MTU пути до endpoint'а Cloudflare:

```
MTU туннеля = PMTU до endpoint − 60
```

60 байт — это накладные расходы WireGuard поверх IPv4: 20 (IP) + 8 (UDP) +
16 (заголовок data-пакета WG) + 16 (тег Poly1305).

PMTU меряется с ноды. `-M do` запрещает фрагментацию, `-s` задаёт полезную
нагрузку, к которой ядро добавит 28 байт (20 IP + 8 ICMP):

```bash
EP=$(jq -r '.endpoint_v4' node-1.account.json | cut -d: -f1); for s in 1472 1452 1422 1372 1332 1272 1232; do ping -M do -s $s -c1 -W2 "$EP" >/dev/null 2>&1 && { echo "PMTU=$((s+28)) -> --mtu $((s+28-60))"; break; }; done
```

Первое сработавшее значение и даёт ответ: например `PMTU=1500` означает
`--mtu 1440`, а `PMTU=1400` — `--mtu 1340`.

Два случая, когда способ не работает:

- **ICMP отфильтрован** — цикл не выведет ничего. Тогда 1280 остаётся
  осознанным консервативным выбором: это минимальный MTU IPv6, ниже которого
  путь не имеет права опускаться.
- **PMTU меряется до Cloudflare, а зависает на конкретном сайте.** Тогда дело
  не в MTU туннеля, а в PMTU дальше по пути, и лечится это со стороны сайта,
  а не подкруткой `--mtu`.

Меняйте по одному значению за раз и проверяйте против исходного симптома, а не
«на глаз».

Если медленно **равномерно**, дело не в MTU, а в userspace-стеке. Смотрите CPU
процесса Xray на ноде. Если он упирается в потолок — это цена native-схемы;
вариант ухода описан в [architecture.md](architecture.md#цена-вопроса).

## Соединения рвутся вразнобой, воспроизвести не получается

Проверьте, не используется ли **один и тот же** файл аккаунта на нескольких
нодах. Это самая неприятная ошибка в этой схеме: ноды выбивают друг друга из
единственной сессии peer'а, при этом каждая локально выглядит здоровой.

```bash
# на каждой ноде — публичные ключи должны отличаться
jq -r .public_key nodes/*.account.json | sort | uniq -d
```

Пустой вывод — хорошо. Любая строка — две ноды делят аккаунт.

Подробнее: [architecture.md](architecture.md#почему-один-аккаунт-на-ноду).

## Как понять, принимает ли сервис новый IP

`warp=on` доказывает только, что пакеты идут через Cloudflare. Ради чего WARP
обычно и ставят на ноду — чтобы хостинговый адрес сменился на потребительский,
который сервисы не режут, — это отдельный вопрос, и проверяется отдельно:

```bash
warp-vps verify -a node-1.account.json --probe ai
```

**Не проверяйте это, дёргая HTML-корень сайта.** `curl https://chatgpt.com`
вернёт `403` откуда угодно, включая домашний браузерный IP: Cloudflare отбивает
curl по TLS-отпечатку, а не по адресу и не по User-Agent (браузерный UA ничего
не меняет — проверено). Такой `403` про вашу репутацию не говорит **ничего**, и
на нём легко сделать ложный вывод «WARP не помогает».

Пресет `ai` спрашивает эндпоинты, которые отвечают честно:

| Эндпоинт | Что означает ответ |
|---|---|
| `.../cdn-cgi/trace` | бот-защитой не прикрыт; `200` плюс строка `ip= loc= warp=` — то, каким сервис видит ваше соединение |
| `api.openai.com/v1/models` | `401` = дошли, просто нет ключа. `403` = вот это уже блокировка |
| `gemini.google.com` | `200` = доступен |

Окончательный ответ всё равно даёт браузер через готовый VPN, а не curl:
логин-флоу, капчи и антифрод смотрят на гораздо больше признаков, чем адрес.

## Что собрать перед тем, как просить помощи

```bash
./warp-vps.sh info    --account <файл>
./warp-vps.sh verify  --account <файл> 2>&1 | tail -40
jq 'del(.private_key, .access_token)' <файл>
```

Третья команда безопасна для пересылки: приватный ключ и токен из неё вырезаны.
Никогда не отправляйте файл аккаунта целиком.
