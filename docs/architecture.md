# Как это устроено

> Всё, что здесь утверждается про поведение Xray, проверено по исходникам
> **v26.3.27** (последний stable) и **v26.7.28** (её ставит Remnawave 3.4.x).
> Общее для обеих: дефолт MTU 1420, `reserved` ровно 3 байта, `noKernelTun`
> работает, `address` принимает и голый адрес, и префикс.
>
> Разошлись они в резолве доменной цели: v26.3.27 идёт в ядровой DNS Xray,
> v26.7.28 — внутрь туннеля через зашитые 1.1.1.1/1.0.0.1. Подробности в
> [remnawave.md](remnawave.md#dns).
>
> Поля тоже разъезжаются: `remoteDNS` есть только в `main` и ни в одном релизе,
> `workers` был в v26.3.27 и исчез в v26.7.28. Go-декодер молча игнорирует
> неизвестные ключи, поэтому поле не из той версии не даёт ни ошибки, ни
> эффекта. Сверяйтесь с тегом на своей ноде: `xray version`.

## Два способа завести WARP на ноде

**Host-туннель.** `wgcf` регистрирует аккаунт, `wg-quick` поднимает ядерный
интерфейс с `Table = 51820`, чтобы не трогать дефолтный маршрут сервера, и
`ip rule fwmark 255 table 51820` заворачивает в него только помеченные пакеты.
Xray помечает свои пакеты через `sockopt.mark`.

**Xray-native (этот проект).** Xray сам собирает и разбирает WireGuard-кадры
поверх обычного UDP-сокета. В системе не появляется ни интерфейса, ни маршрута,
ни правила.

Мы выбрали второй. Ниже — почему, и чем за это платим.

---

## Цена вопроса

Native-схема гоняет пакеты через userspace-стек (gVisor netstack), а не через
ядро. На большом потоке это заметно по CPU. Host-схема быстрее.

Взамен исчезает целый класс отказов, и это главный аргумент.

### Отказ, которого здесь нет: строгий rp_filter

В host-схеме туннель асимметричен by design. Помеченные пакеты уходят через
`warp` в таблице 51820, а дефолтный маршрут сервера остаётся на основном
интерфейсе. Расшифрованные ответы возвращаются на `warp` **без метки** — правило
`fwmark` не срабатывает, лукап уходит в main table, упирается в дефолт через
основной NIC, входящий интерфейс не совпадает. При `rp_filter = 1` ядро такой
пакет молча дропает.

Симптом отвратительный: `wg show` показывает свежий handshake, интерфейс
`ACTIVE`, а трафика нет.

Хуже того, `wg-quick` эту ситуацию не закрывает сам. Его
`sysctl net.ipv4.conf.all.src_valid_mark=1` вызывается внутри `add_default()`, а
до него доходит только ветка с `Table = auto` или пустым `Table`. С явным
`Table = 51820` берётся другая ветка, и `src_valid_mark` не выставляется никогда.

Значит, `rp_filter` обязан понизить кто-то на хосте — и не забыть закрепить в
`/etc/sysctl.d/`, иначе первый же ребут вернёт строгий режим и туннель потемнеет
с идеально здоровым handshake.

**В native-схеме ничего этого нет.** Нет интерфейса — нет асимметричного
маршрута — нет обратного пути, который ядро могло бы отбросить. Пакеты для
Cloudflare выходят обычным UDP из процесса Xray и возвращаются туда же.

### Отказ, которого здесь тоже нет: контейнер

Xray на ноде Remnawave живёт в контейнере. `SO_MARK` требует `CAP_NET_ADMIN`,
поэтому host-схема тянет за собой `cap_add: NET_ADMIN` и `network_mode: host`
(иначе метка не дойдёт до host-овых `ip rule`).

Native-схеме не нужно ни то, ни другое — при условии `noKernelTun: true`.

## Почему `noKernelTun: true` по умолчанию

Xray-core умеет два транспорта для своего WireGuard:

- `createKernelTun()` — ядерный TUN, быстрее;
- `CreateNetTUN()` — userspace gVisor.

Выбор делает поле `noKernelTun` (`infra/conf/wireguard.go` →
`proxy/wireguard/config.go`, функция выбора туннеля).

Ядерный путь требует `CAP_NET_ADMIN` и при старте пишет `rp_filter` в
`/proc/sys`. Внутри непривилегированного контейнера `/proc/sys` смонтирован
read-only, и Xray падает:

```
failed to disable ipv4 rp_filter for all: read-only file system
```

Отсюда дефолт `true`.

Стоит знать, что Xray подстраховывается и сам: `KernelTunSupported()` в
`proxy/wireguard/tun_linux.go` читает капабилити текущего процесса через
`unix.Capget` и проверяет бит `CAP_NET_ADMIN`; если его нет, выбирается gVisor
независимо от флага. То есть `noKernelTun: true` — это гарантия, а не
единственное, что стоит между вами и упавшим стартом.

`--kernel-tun` возвращает быстрый путь, если контейнер привилегированный и вы
сознательно берёте на себя это требование.

---

## Почему один аккаунт на ноду

Аккаунт WARP — это пара ключей WireGuard. Cloudflare идентифицирует peer по
публичному ключу.

Две ноды с одной парой ключей — **один и тот же peer**. WireGuard хранит одну
активную сессию на peer: handshake со второй ноды вытесняет сессию первой, потом
первая переустанавливает свою и вытесняет вторую. Ноды по очереди выбивают друг
друга, обе локально выглядят подключёнными, а пользователи получают рваные
соединения, которые не воспроизводятся при проверке «руками».

`warp-vps batch` регистрирует независимые аккаунты именно поэтому.

---

## Почему MTU 1280

Xray по умолчанию ставит 1420 (`if c.MTU == 0 { config.Mtu = 1420 }`). Для WARP
это много: поверх пути провайдера ложится заголовок WireGuard, и пакеты около
верхней границы начинают теряться.

Симптом характерный и легко списывается на «медленный сервер»: короткие запросы
проходят мгновенно, а тяжёлые страницы, загрузки и всё, что упирается в MSS,
виснет на середине.

1280 — минимальный MTU IPv6, ниже которого путь не имеет права опускаться.
Проходит везде.

В host-схеме ту же задачу решают TCP MSS clamping'ом в `mangle POSTROUTING`.
Здесь он не нужен: MTU задан на самом туннеле, и Xray анонсирует MSS сам.

---

## Почему `reserved`, и откуда он берётся

WARP кладёт идентификатор клиента (`client_id`) в поле `reserved` заголовка
WireGuard. Xray принимает его как массив ровно из 3 байт и отвергает любую другую
длину (`"reserved" should be empty or 3 bytes`).

Тонкость, из-за которой в проекте нет `wgcf`: **`wgcf` этого поля не сохраняет**.

- `wgcf-account.toml` содержит ровно четыре ключа: `device_id`, `access_token`,
  `private_key`, `license_key`.
- `wgcf generate` пишет профиль из `PrivateKey`, `Address v4/v6`, `PublicKey`
  и `Endpoint` — `client_id` в него не попадает.

То есть из файлов wgcf `reserved` не восстановить в принципе. Он живёт только в
ответе API (`GET /{apiVersion}/reg/{device_id}` → `config.client_id`, base64 над
тремя байтами). Мы обращаемся к тому же API и сохраняем это поле сразу.

## Профиль запроса к API Cloudflare

Официальный клиент ходит с очень узким TLS-профилем, и API отвечает
`403 (error 1020)`, если запрос на него не похож:

| Параметр | Значение | В curl |
|---|---|---|
| TLS | ровно 1.2 (`Min == Max`) | `--tlsv1.2 --tls-max 1.2` |
| HTTP/2 | выключен | `--http1.1` |
| User-Agent | `okhttp/3.12.1` | `-H` |
| CF-Client-Version | `a-6.3-1922` | `-H` |
| API version | `v0a1922` | в пути |

`--tlsv1.2` задаёт только нижнюю границу. Без `--tls-max 1.2` curl предложит
1.3, и запрос отобьётся. Это не перестраховка, это воспроизведённый вручную
случай.

## Генерация ключей без wireguard-tools

`wg genkey` есть не везде, а тянуть ради него пакет не хочется. X25519 умеет
OpenSSL, и ключ в DER имеет фиксированную структуру, где последние 32 байта —
сырой ключ:

```
приватный (48 байт):  302e020100300506032b656e04220420 | <32 байта>
публичный (44 байта):  302a300506032b656e032100         | <32 байта>
```

Отсюда:

```bash
openssl genpkey -algorithm X25519 -out k.pem
openssl pkey -in k.pem          -outform DER | tail -c 32 | base64   # private
openssl pkey -in k.pem -pubout  -outform DER | tail -c 32 | base64   # public
```

Скаляр OpenSSL клампит сам (RFC 7748), так что результат совпадает с тем, что
дал бы `wg genkey`. Если `wg` в системе есть — используется он.
