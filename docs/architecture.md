# Как это устроено

> Проверено по исходникам: `wireguard-tools` (`wg-quick/linux.bash`), ядро Linux
> (`net/ipv4/route.c`), Xray-core **v26.7.28** (её ставит Remnawave 3.4.x) и
> **v26.3.27**. Версию на ноде смотрите через `xray version` — поля и поведение
> между релизами расходятся.

## Схема

```
клиент ──VLESS/Reality──▶ Xray на ноде
                             │
                             ├─ правило не совпало ──▶ freedom (обычный выход, eth0)
                             │
                             └─ совпало ──▶ outbound "warp"
                                              freedom + sockopt.interface: "warp"
                                              │  SO_BINDTODEVICE
                                              ▼
                                           интерфейс warp (ядерный WireGuard)
                                              │
                                              ▼
                                           Cloudflare WARP ──▶ цель
```

## Почему нет ни одного маршрута

`Table = off` в `[Interface]` — центральное решение. В `wg-quick`:

```bash
add_route() {
    local proto=-4
    [[ $1 == *:* ]] && proto=-6
    [[ $TABLE != off ]] || return 0     # ← выход на первой строке
```

То есть после поднятия интерфейса в системе нет ни одного маршрута через
`warp`, а `ip route` выглядит ровно так же, как до установки.

Тогда почему пакет доходит? Потому что ядро специально это разрешает.
`net/ipv4/route.c`, ветка после неудачного `fib_lookup`, когда задан
исходящий интерфейс:

```c
err = fib_lookup(net, fl4, res, 0);
if (err) {
        res->fi = NULL;
        res->table = NULL;
        if (fl4->flowi4_oif && ...) {
                /* Apparently, routing tables are wrong. Assume,
                 * that the destination is on link.
                 *
                 * WHY? DW.
                 * Because we are allowed to send to iface
                 * even if it has NO routes and NO assigned
                 * addresses. When oif is specified, routing
                 * tables are looked up with only one purpose:
                 * to catch if destination is gatewayed, rather than
                 * direct. ...
                 */
```

`SO_BINDTODEVICE` задаёт `flowi4_oif`. Маршрут не нашёлся — ядро считает, что
адресат за этим интерфейсом, и отправляет туда.

### Что из этого следует

- **Нечему протечь.** Нет `ip rule` и нет записи в таблице, которые могли бы
  пережить упавший юнит и потом молча уводить трафик не туда.
- **`rp_filter` не при делах.** Схемы с `fwmark` + отдельной таблицей ломаются
  на строгом `rp_filter`: обратный трафик приходит без метки, лукап уходит в
  main table и пакет дропается при `rp_filter=1`. Здесь политики маршрутизации
  нет вообще.
- **Хост не меняет поведение.** Собственный трафик ноды — обновления, панель,
  SSH — как ходил через `eth0`, так и ходит.
- **Цена:** привязка обязана быть явной. Забыли `sockopt.interface` — трафик
  пошёл мимо туннеля, с реального IP, без единой ошибки в логах.

## Почему `reserved` здесь не нужен

WARP кладёт идентификатор клиента (`client_id`) в поле `reserved` заголовка
WireGuard. В userspace-реализациях его выставляют вручную — например, в
`wireguard`-outbound Xray это обязательные 3 байта.

**Ядерный WireGuard этого поля не выставляет.** Поэтому в host-схеме `reserved`
не участвует и не сохраняется: туннель аутентифицируется парой ключей. Если
встретите инструкцию, требующую `reserved` для `wg-quick`, — она про другую
схему.

## Почему `wgcf` не нужен

`wgcf` — обёртка над API Cloudflare. Установщики скачивают её бинарь с GitHub,
делают `chmod +x` и запускают от root; подписи нет, контрольная сумма не
проверяется, а из тех же релизов её брать бессмысленно.

Мы делаем те же вызовы сами:

```
POST /{apiVersion}/reg          → device id, token, адрес, ключ пира, endpoint
PUT  /{apiVersion}/reg/{id}/account → применить ключ WARP+
```

Пара ключей X25519 генерируется локально. Если есть `wireguard-tools` —
через `wg genkey`; иначе через OpenSSL, где ключ в DER имеет фиксированную
структуру и последние 32 байта — сырой ключ:

```
приватный (48 байт):  302e020100300506032b656e04220420 | <32 байта>
публичный (44 байта):  302a300506032b656e032100         | <32 байта>
```

Скаляр OpenSSL клампит сам (RFC 7748), так что результат совпадает с `wg genkey`.

## Профиль запроса к API

Официальный клиент ходит с узким TLS-профилем, и API отвечает `403 (error 1020)`,
если запрос на него не похож:

| Параметр | Значение | В curl |
|---|---|---|
| TLS | ровно 1.2 (`Min == Max`) | `--tlsv1.2 --tls-max 1.2` |
| HTTP/2 | выключен | `--http1.1` |
| User-Agent | `okhttp/3.12.1` | `-H` |
| CF-Client-Version | `a-6.3-1922` | `-H` |
| Версия API | `v0a1922` | в пути |

`--tlsv1.2` задаёт только нижнюю границу: без `--tls-max 1.2` curl предложит
1.3 и получит отказ. Это воспроизведённый случай, а не перестраховка.

## Почему MTU 1280

Поверх пути провайдера ложится заголовок WireGuard, и пакеты у верхней границы
начинают теряться. Симптом характерный: короткие запросы летают, тяжёлые
страницы и загрузки виснут на середине.

1280 — минимальный MTU IPv6, ниже которого путь не имеет права опускаться;
проходит везде. Если и его мало, значение выводится измерением, а не подбором —
см. [troubleshooting.md](troubleshooting.md).

## Watchdog

Systemd-таймер, а не cron: переживает пропущенный тик (`Persistent=true`),
пишет в журнал вместо самодельной ротации файла и умеет зависеть от
`wg-quick@warp`.

Проверка идёт по двум признакам:

1. возраст handshake (порог 180 с);
2. **что докладывает Cloudflare** — `curl --interface warp .../cdn-cgi/trace`
   должен вернуть `warp=on` или `warp=plus`.

Второй пункт важнее первого: туннель может быть жив и пинговаться, уже не
будучи WARP. Пинг остаётся запасным вариантом, если сам trace недоступен.

При отказе — backoff `3 → 6 → 12 → 24 → 30` минут и **смена endpoint** на
случайный из anycast-диапазонов Cloudflare. Фиксированный интервал даёт сотни
рестартов WireGuard в сутки при полной блокировке — заметная сигнатура, которая
вдобавок не помогает. Ручной `rotate` сбрасывает счётчик, чтобы watchdog не
досиживал получасовой cooldown после вашего вмешательства.
