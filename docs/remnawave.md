# Интеграция с Remnawave

## Где живёт конфиг

Xray-конфиг ноды Remnawave задаётся **в панели**, а не на сервере. Нода получает
его от панели и передаёт в Xray. Практическое следствие для нас: чтобы включить
WARP на части нод, на эти ноды заходить не нужно вообще — вся работа делается в
панели.

Как именно конфиг раскладывается по нодам, зависит от версии панели: в одних
это единый шаблон Xray на всю инсталляцию, в других — конфиг-профили, назначаемые
нодам по отдельности.

> **Проверьте на своей панели**, прежде чем править: если конфиг один на всех, то
> добавленный outbound получат **все** ноды. Само по себе это не страшно —
> outbound без правила маршрутизации трафик не забирает, — но правило `routing`
> тогда тоже применится ко всем.

Ниже — оба сценария.

---

## Сценарий A: WARP на части нод (отдельный конфиг-профиль)

1. Заведите отдельный WARP-аккаунт **для каждой** ноды:

   ```bash
   ./warp-vps.sh batch --count 3 --prefix eu --out-dir ./nodes
   ```

   Получите `nodes/eu-1.account.json` … `eu-3.account.json` и рядом
   `eu-N.outbound.json`.

   Почему по одному на ноду, а не один на всех — см.
   [architecture.md](architecture.md#почему-один-аккаунт-на-ноду).

2. Проверьте каждый **до** того, как он попадёт в панель:

   ```bash
   ./warp-vps.sh verify --account nodes/eu-1.account.json
   ```

   Пока не увидели `warp=on` — в панель не несём.

3. Возьмите содержимое `eu-1.outbound.json` и добавьте его в массив `outbounds`
   конфига того профиля, который назначен этой ноде.

4. Добавьте правило маршрутизации в `routing.rules` **выше** всех правил,
   отправляющих трафик в `direct`.

---

## Сценарий B: один конфиг на всю инсталляцию

Тогда WARP-выход будет физически присутствовать на всех нодах, но пользоваться
им будут только те домены, которые вы перечислите в правиле. Если этого
достаточно — сценарий рабочий и самый простой.

Если нужно, чтобы разные ноды вели одни и те же домены по-разному, единого
конфига не хватит: нужны конфиг-профили (Сценарий A).

---

## Что именно вставлять

```bash
./warp-vps.sh generate \
  --account nodes/eu-1.account.json \
  --rules "geosite:openai,geosite:google,domain:chatgpt.com,domain:claude.ai" \
  --full
```

Выдаст:

```json
{
  "outbounds": [ { "tag": "warp", "protocol": "wireguard", "settings": { ... } } ],
  "routing": { "rules": [ { "type": "field", "domain": [ ... ], "outboundTag": "warp" } ] }
}
```

`outbounds[0]` кладём в `outbounds`, `routing.rules[0]` — в `routing.rules`.

---

## Порядок правил решает всё

Xray применяет **первое совпавшее** правило, а не самое специфичное. Поэтому:

```jsonc
"routing": {
  "rules": [
    { "type": "field", "domain": ["geosite:openai"], "outboundTag": "warp" },   // ✅ выше
    { "type": "field", "network": "tcp,udp", "outboundTag": "direct" }          // catch-all ниже
  ]
}
```

Если поменять их местами, `direct` заберёт весь трафик и WARP-outbound останется
мёртвым грузом — при этом в панели всё будет выглядеть настроенным.

## DNS

Правило по домену срабатывает до резолва, но дальше имя всё равно кто-то
резолвит. Если резолвер ходит мимо туннеля, geo-управляемый CDN ответит адресами
для **реального** местоположения ноды, и смысл WARP-выхода теряется.

```bash
./warp-vps.sh generate -a nodes/eu-1.account.json --remote-dns "1.1.1.1"
```

Это добавит в outbound `remoteDNS`, и имена для этого выхода будут резолвиться
изнутри туннеля.

## Требования к контейнеру ноды

Никаких. В этом и смысл схемы:

- `privileged: true` — **не нужен**
- `cap_add: NET_ADMIN` — **не нужен**
- `network_mode: host` — **не нужен**
- `sysctl` на хосте — **не трогаем**

Единственное требование — Xray внутри ноды должен уметь `protocol: "wireguard"`
и понимать `noKernelTun`. Поле существует в Xray-core начиная как минимум с
`v24.12.31`, так что любая актуальная нода подходит.

Если контейнер ноды у вас всё-таки привилегированный, `--kernel-tun` переключит
на ядерный путь — быстрее, но требует прав на запись в `/proc/sys`.

## Проверка после раскатки

С самой ноды, через уже работающий конфиг, проще всего убедиться так:

```bash
docker exec -it <remnanode> sh -c 'wget -qO- https://cloudflare.com/cdn-cgi/trace' | grep -E 'warp|ip='
```

Это покажет выход **самой ноды** (должен быть `warp=off` — нода ходит напрямую).
Реальную проверку WARP-выхода даёт клиентский запрос к домену из правила: откройте
его через VPN и посмотрите определившуюся геолокацию.

Надёжнее — проверить конфиг до раскатки: `warp-vps verify` делает ровно это,
поднимая одноразовый Xray с тем же outbound.
