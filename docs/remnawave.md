# Интеграция с Remnawave

## Где живёт конфиг

Xray-конфиг ноды Remnawave задаётся **в панели**, а не на сервере. Нода получает
его от панели и передаёт в Xray. Практическое следствие для нас: чтобы включить
WARP на части нод, на эти ноды заходить не нужно вообще — вся работа делается в
панели.

Как именно конфиг раскладывается по нодам, зависит от версии панели: в одних
это единый шаблон Xray на всю инсталляцию, в других — конфиг-профили, назначаемые
нодам по отдельности.

> **Проверьте на своей панели**, прежде чем править: если конфиг один на всех, то
> добавленный outbound получат **все** ноды. Само по себе это не страшно —
> outbound без правила маршрутизации трафик не забирает, — но правило `routing`
> тогда тоже применится ко всем.

Ниже — оба сценария.

---

## Сценарий A: WARP на части нод (отдельный конфиг-профиль)

1. Заведите отдельный WARP-аккаунт **для каждой** ноды:

   ```bash
   ./warp-vps.sh batch --count 3 --prefix eu --out-dir ./nodes
   ```

   Получите `nodes/eu-1.account.json` … `eu-3.account.json` и рядом
   `eu-N.outbound.json`.

   Почему по одному на ноду, а не один на всех — см.
   [architecture.md](architecture.md#почему-один-аккаунт-на-ноду).

2. Проверьте каждый **до** того, как он попадёт в панель:

   ```bash
   ./warp-vps.sh verify --account nodes/eu-1.account.json
   ```

   Пока не увидели `warp=on` — в панель не несём.

3. Возьмите содержимое `eu-1.outbound.json` и добавьте его в массив `outbounds`
   конфига того профиля, который назначен этой ноде.

4. Добавьте правило маршрутизации в `routing.rules` **выше** всех правил,
   отправляющих трафик в `direct`.

---

## Сценарий B: один конфиг на всю инсталляцию

Тогда WARP-выход будет физически присутствовать на всех нодах, но пользоваться
им будут только те домены, которые вы перечислите в правиле. Если этого
достаточно — сценарий рабочий и самый простой.

Если нужно, чтобы разные ноды вели одни и те же домены по-разному, единого
конфига не хватит: нужны конфиг-профили (Сценарий A).

---

## Что именно вставлять

```bash
./warp-vps.sh generate \
  --account nodes/eu-1.account.json \
  --rules "geosite:openai,geosite:google,domain:chatgpt.com,domain:claude.ai" \
  --full
```

Выдаст:

```json
{
  "outbounds": [ { "tag": "warp", "protocol": "wireguard", "settings": { ... } } ],
  "routing": { "rules": [ { "type": "field", "domain": [ ... ], "outboundTag": "warp" } ] }
}
```

`outbounds[0]` кладём в `outbounds`, `routing.rules[0]` — в `routing.rules`.

---

## Где НЕ надо запускать merge

Конфиг Xray на ноде Remnawave — **панельный**. Нода получает его от панели и
передаёт Xray. Правка, сделанная в файле на ноде, живёт до ближайшей
синхронизации, после чего откатывается молча: ошибок нигде нет, WARP просто
перестаёт работать, и искать причину вы будете в туннеле.

Правильный порядок: выгрузить конфиг из панели → прогнать `merge` на этой копии →
вставить результат обратно в панель.

`merge` отказывается работать с путями, похожими на панельные
(`*/remnanode/*`, `*/opt/remnanode*` и т. п.). Обойти можно флагом
`--force-path`, но подумайте дважды.

---

## Вставка одной командой

Руками это править не обязательно — и лучше не надо, потому что ошибиться можно
двумя разными способами (см. следующий раздел). `merge` делает вставку сам,
предварительно сняв резервную копию и проверив результат самим Xray
(`xray run -test`), если бинарь доступен:

```bash
./warp-vps.sh merge \
  --config /path/to/xray-config.json \
  --account nodes/eu-1.account.json \
  --rules "geosite:openai,domain:chatgpt.com,domain:claude.ai"
```

Что он гарантирует:

- outbound **дописывается в конец** массива, никогда не в начало;
- правило вставляется **выше** первого catch-all, если он есть, и в конец, если
  его нет;
- повторный запуск с `--replace` не плодит дубликаты — старый outbound и старое
  правило с тем же тегом убираются;
- перед записью создаётся `<config>.<timestamp>.bak`, а сам файл пишется через
  временный, так что оборванная запись не оставит битый конфиг;
- `--dry-run` печатает результат, ничего не трогая.

Откат — вернуть `.bak` и перечитать конфиг.

---

## Порядок правил решает всё

Xray применяет **первое совпавшее** правило, а не самое специфичное. Поэтому:

```jsonc
"routing": {
  "rules": [
    { "type": "field", "domain": ["geosite:openai"], "outboundTag": "warp" },   // ✅ выше
    { "type": "field", "network": "tcp,udp", "outboundTag": "direct" }          // catch-all ниже
  ]
}
```

Если поменять их местами, `direct` заберёт весь трафик и WARP-outbound останется
мёртвым грузом — при этом в панели всё будет выглядеть настроенным.

### Если catch-all правила нет вообще

Частый случай: в `routing.rules` перечислены только BLOCK-правила, а «всё
остальное» никуда явно не отправляется. Тогда работает вторая, менее известная
механика Xray — **не совпавший ни с чем трафик уходит в первый outbound массива**
(`app/proxyman/outbound` присваивает `defaultHandler` при первом `AddHandler`,
а диспетчер откатывается на него, когда роутер не дал ответа).

Практический вывод: в такой конфигурации WARP-outbound **нельзя ставить первым**
в `outbounds`. Иначе через WARP пойдёт вообще весь трафик ноды, включая тот, для
которого никаких правил не писали. Правило же можно спокойно дописывать в конец —
перекрывать его нечем.

`merge` соблюдает оба условия сам.

## DNS

Правило по домену срабатывает до резолва, но дальше имя всё равно кто-то
резолвит, и от того, кто именно, зависит, какие адреса вернёт geo-управляемый CDN.

**Кто резолвит — зависит от версии Xray.** Это не мелочь: от неё зависит,
увидит ли geo-управляемый CDN геолокацию ноды или выхода WARP.

| Версия | Резолв доменной цели | Следствие |
|---|---|---|
| v26.3.27 | `h.dns.LookupIP` — ядровой DNS-модуль Xray | имена разрешаются с реального IP ноды |
| v26.7.28 | `h.tnet.LookupHost` — **внутри туннеля**, 1.1.1.1/1.0.0.1 зашиты в код | резолв и соединение делят один выход |

Проверяется по `proxy/wireguard/client.go`, функция `resolveRemote`. Версию на
ноде смотрите в логах Remnawave (`XRay Core: vXX.Y.Z`) или через `xray version`.

На v26.7.28 (её ставит Remnawave 3.4.x) делать ничего не нужно — резолв уже идёт
через туннель, и настройки `dns` основного конфига на этот outbound не влияют,
как и правило `inboundTag: ["dns_inbound"] → DIRECT`.

> **Ловушка с полями между версиями.** В ветке `main` есть `remoteDNS`,
> переключающий резолвер; **ни в одном релизе его нет** — проверено для
> v24.9.30 … v26.7.28. В v26.3.27 был `workers`, в v26.7.28 его уже нет.
> Go-декодер молча игнорирует неизвестные ключи, поэтому поле не из той версии
> не даст ни ошибки, ни эффекта. Сверяйтесь с тем тегом, что стоит на ноде.

Если геолокация резолва принципиальна, вариант в рамках released Xray — завести
отдельный DNS-сервер в секции `dns` с `domains`-привязкой к тем же AI-доменам и
не отправлять его в `DIRECT`. Это отдельная правка, инструментом она не делается.

---

### `domainStrategy: "IPIfNonMatch"` ничего здесь не ломает

Можно было бы ожидать, что IP-правило, стоящее выше нашего (например
`ip: ["geoip:private"] → BLOCK`), заставит ноду резолвить домен ещё до того, как
очередь дойдёт до WARP-правила. Этого не происходит: `IPIfNonMatch` работает в
**два прохода** (`app/router/router.go`, `pickRouteInternal`). Первый проход идёт
вообще без DNS-клиента в контексте, поэтому IP-правила против доменной цели не
срабатывают. Второй проход, уже с резолвом, запускается только если на первом не
совпало **ничего**.

Доменное WARP-правило совпадает на первом проходе, значит лишнего резолва с
реального IP ноды не будет.

## Требования к контейнеру ноды

Никаких. В этом и смысл схемы:

- `privileged: true` — **не нужен**
- `cap_add: NET_ADMIN` — **не нужен**
- `network_mode: host` — **не нужен**
- `sysctl` на хосте — **не трогаем**

Единственное требование — Xray внутри ноды должен уметь `protocol: "wireguard"`
и понимать `noKernelTun`. Поле существует в Xray-core начиная как минимум с
`v24.12.31`, так что любая актуальная нода подходит.

Если контейнер ноды у вас всё-таки привилегированный, `--kernel-tun` переключит
на ядерный путь — быстрее, но требует прав на запись в `/proc/sys`.

## Проверка после раскатки

С самой ноды, через уже работающий конфиг, проще всего убедиться так:

```bash
docker exec -it <remnanode> sh -c 'wget -qO- https://cloudflare.com/cdn-cgi/trace' | grep -E 'warp|ip='
```

Это покажет выход **самой ноды** (должен быть `warp=off` — нода ходит напрямую).
Реальную проверку WARP-выхода даёт клиентский запрос к домену из правила: откройте
его через VPN и посмотрите определившуюся геолокацию.

Надёжнее — проверить конфиг до раскатки: `warp-vps verify` делает ровно это,
поднимая одноразовый Xray с тем же outbound.
