# Два профиля: весь трафик и только AI

Два готовых варианта. Отличаются они ровно одним правилом маршрутизации —
outbound в обоих одинаковый.

| Профиль | Правило | Что уходит в WARP |
|---|---|---|
| `warp-all` | `{"type":"field","network":"tcp,udp","outboundTag":"warp"}` | всё, что не забрали правила выше |
| `warp-ai` | `{"type":"field","domain":[…],"outboundTag":"warp"}` | только домены AI-сервисов |

Сборка. `merge` берёт существующий конфиг и возвращает **целый** конфиг,
готовый к вставке в панель:

```bash
# весь трафик
warp-vps merge -c panel-config.json --all-traffic

# только AI
warp-vps merge -c panel-config.json --rules ai
```

`panel-config.json` — это выгруженная из панели копия. Не файл на ноде: там
конфиг панельный и правка не переживёт синхронизацию.

Если нужен не целый конфиг, а только два куска для ручной вставки —
`generate --full`. Несмотря на название, это **фрагмент**
(`{outbounds:[…], routing:{rules:[…]}}`), а не готовый конфиг:

```bash
warp-vps outbound --all-traffic --full
```

Список доменов и обоснование, что в него не вошло, — в
[templates/rules-ai.json](../templates/rules-ai.json).

## Куда встаёт правило и почему это важно

В обоих случаях правило вписывается **пятым**, после существующих:

```
0  DIRECT  inboundTag: dns_inbound        ← DNS остаётся прямым
1  BLOCK   ip: geoip:private
2  BLOCK   domain: geosite:private
3  BLOCK   domain: geosite:category-ads-all
4  warp    ← сюда
```

Порядок не косметический, каждая строка выше нашей что-то защищает:

- **`dns_inbound → DIRECT` должен остаться выше.** Иначе собственные
  DNS-запросы Xray пойдут в туннель, который в момент старта ещё не поднят.
- **`geoip:private` выше** — иначе при `--all-traffic` в туннель уедет трафик к
  приватным диапазонам, включая обращения внутри самого хоста.
- **BLOCK-правила выше** — реклама остаётся заблокированной и на AI-доменах,
  а не проксируется через WARP.

## Профиль можно назначить нескольким нодам

В host-схеме это разрешено, и в этом её приятное отличие. Конфиг Xray не
содержит никаких ключей WARP — только `sockopt.interface: "warp"`, то есть имя
интерфейса. Ключи лежат на каждой ноде в `/etc/wireguard/warp.conf`, и `install`
регистрирует **своё** устройство на каждой.

Это существенно. Две ноды с одной парой ключей WireGuard были бы для Cloudflare
одним peer'ом: сессия переезжает на адрес последнего валидного handshake, ноды
по очереди выбивают друг друга, и каждая при этом локально выглядит здоровой.
Здесь такую ошибку сделать нечем — копировать между нодами нечего.

## Чем платите за `--all-traffic`

Профиль «весь трафик» рабочий, но у него есть две цены, которые лучше знать
заранее, чем ловить под нагрузкой.

**CPU.** Шифрование идёт в ядре, поэтому накладные расходы куда меньше, чем у
userspace-туннеля, но они не нулевые: на слабой ноде полный поток через
WireGuard заметен. Смотрите `si` (softirq) в `top`, а не только пользовательский CPU.

**Шейпинг Cloudflare.** Бесплатный WARP из датацентровых подсетей режется тем
сильнее, чем больше через него льют. Для полного туннеля имеет смысл WARP+:

```bash
warp-vps license --key <ключ>
```

Померить, а не гадать:

```bash
warp-vps verify --probe ai    # факт выхода через WARP
# затем на ноде под нагрузкой:
top -bn1 | head -5            # смотреть на %si (softirq)
```
